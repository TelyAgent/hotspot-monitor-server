> **Canonical contract.** 本文件是热点内容生产线、账号映射和账号 Skill 响应规则的唯一专项合同。Event、风险、人工发布和追踪遵循平台总规则。

# 热点内容生成 Skill SPEC

## Why

平台需要把来自热搜、主题圈、未来事件和人工入口的 Event，以同一种受事实约束的输入交给多个账号 Skill。生产线决定生成什么类型的内容，账号决定由谁发布；系统既能稳定覆盖每个热点，也能在流量增加时通过新增同类型账号扩容。

## Capabilities

- **CAP-1 三条基础生产线**
  - **intent:** 每个自动响应 Event 都可以获得快讯型、长文/深度分析型和产品承接型内容。
  - **success:** 三条生产线均读取同一 Event Context Pack，并为每个可用绑定账号生成 3 条审核草稿或返回可追溯异常。
- **CAP-2 生产线与账号映射**
  - **intent:** 系统可以让一条生产线绑定一个或多个发布账号，以支持容量扩展。
  - **success:** 每个 `Event × Account × Skill Version` 只创建一个 Account Response Task；新增同类型账号不会改变生产线规则或复用其他账号候选。
- **CAP-3 产品账号全量响应**
  - **intent:** PredX 产品账号对每个路由 Event 都能以真实且合适的方式出现。
  - **success:** 每个任务均生成 3 条 `market_bridge`、`ambient_brand` 或 `quiet_presence` 草稿；没有真实市场关系时不拒绝响应，也不虚构产品关联。
- **CAP-4 人设账号独立判断**
  - **intent:** 九个人设账号可以按各自运营 Skill 判断是否适合响应以及采用何种行动。
  - **success:** 每个 Skill 返回参与、观察或跳过；参与账号生成 3 条账号专属候选，引用或评论具有真实目标帖 URL。
- **CAP-5 候选交付**
  - **intent:** 运营人员可以从有差异的候选中选择、修改或重新生成。
  - **success:** 每个触发响应的账号任务正常交付 3 条 DRAFT；重新生成仍返回 3 条，历史版本和用户要求可追溯。

## 1. 统一输入

所有 Skill 只读取 Event 生成的 `Event Context Pack`，不得直接读取页面上的 Event Card。Event Card 是给人查看和校正的页面记录；Event Context Pack 是不同事件源进入内容和营销模块前的统一结构化数据合同。

最小输入包括：

- `event_id`、事件标题和一句话事实摘要；
- 已确认事实、未确认项、冲突说法和 Expression Boundary；
- Evidence Record、来源文章或代表帖子；
- 事实时间、短期上下文和最多 3 条关联 Event；
- `trend_context`、`topic_circle_context`、`schedule_context` 等实际存在的来源扩展；
- 目标账号、账号 Skill 版本、目标平台、语言和请求格式；
- 产品承接需要的产品资料、真实市场、时间戳市场数据、落地页和允许使用的链接。

缺失字段保持空值。Skill 不得补造事实、来源、市场、价格、产品能力或链接。

## 2. 三条基础生产线

| 正式名称 | Skill | 内容职责 | 单账号固定输出 |
|---|---|---|---|
| 快讯型 | `respond-with-breaking-brief` | 把热点压缩为可快速扫描的单一事实更新 | 3 条 X 快讯草稿 |
| 长文/深度分析型 | `develop-hotspot-deep-dive` | 解释背景、已知与未知、关键影响和后续观察点 | 3 条分析草稿；默认 100–180 英文词，复杂事件最高 500 词 |
| 产品承接型 | `bridge-hotspot-to-product` | 以 PredX 产品账号对热点作适当品牌或市场承接 | 3 条产品账号草稿 |

共同规则：

1. 每个自动响应 Event 默认触发三条基础生产线。
2. 每条生产线可以绑定一个或多个同类型账号。
3. 每个绑定账号分别建立 Account Response Task，并分别生成 3 条账号专属草稿。
4. 候选不能跨账号复用；单个账号或 Skill 失败不阻塞其他账号。
5. 三条生产线只生成审核草稿，不自动发布。

### 2.1 快讯型

- 单条只表达一个核心事实，通常为 1–2 句。
- 不做深度分析，不表达个人立场，不进行产品承接。
- 可使用 `JUST IN`、`LIVE` 或 `UPDATE`；`BREAKING` 只用于重大且事实明确的事件，信息有限或存在冲突时不得使用。

### 2.2 长文/深度分析型

- 解释事件背景、专业信息、为什么值得关注以及下一观察点。
- 明确区分已知事实、未知信息和合理分析。
- 可读取最多 3 条关联 Event。
- 默认不承担产品转化；只有上游明确提供产品语境或写作要求时，才可加入不越界的产品上下文。

### 2.3 产品承接型

产品 Skill 不判断“要不要响应”，不得返回 `NO_PRODUCT`。每个路由 Event 都必须生成 3 条草稿：

- `market_bridge`：存在真实、可证明的预测市场问题、市场上下文或结算关系。
- `ambient_brand`：没有真实市场关系时，事件正文独立成立，再使用克制的品牌名、Logo 或已提供的通用链接；不得声称 Event 与 PredX 市场有关。
- `quiet_presence`：伤亡、灾难、私人困境或安全危机等敏感事件，只以 PredX 账号克制发布事实，不在正文加入商业露出、链接、CTA 或预测框架。

准确市场链接、价格、概率、结算规则和产品能力必须来自当前配置和证据。三条候选可以在表达、开头、信息组织或允许的品牌呈现上形成差异，但不能制造三套事实。

## 3. 生产线与账号关系

生产线定义内容能力，账号定义发布身份，两者不是同一个对象。首期通常为每条基础生产线配置一个基础账号；快讯量增大时，可为快讯生产线增加第二个或更多快讯账号。新增账号后，每个账号仍拥有独立任务、独立 3 条候选、独立发布状态和独立容量。

唯一任务边界为：

```text
Event × Account × Skill Version
```

同一 Event 同时被热搜、主题圈或未来事件触发时，复用同一账号任务，不重复创建。

## 4. 九个人设账号 Skill

以下 Skill 是独立账号运营规则，不只是文风模板：

| 账号 Skill | 最佳内容场景 |
|---|---|
| Nick Preszler | 机制、激励、指标误读和二阶洞察 |
| Manifold Markets | 社区原生预测问题、参与和规则解释 |
| WatcherGuru | 金融、加密、政策和机构性快讯 |
| RohOnChain | 工具、研究、教育路径和资源清单 |
| Unusual Whales | 公司、监管、政治、资金与利益后果 |
| Daily Loud | 明星、音乐、体育、创作者和病毒事件 |
| Pubity | 大众化、积极、可分享的成就与事实卡 |
| Nate Silver | 概率校准、基准、激励与可证伪分析 |
| Domer | 预测市场规则、结算、资金流、异常与复盘 |

每个 Event 分别调用各账号 Skill：

1. Skill 返回 `participate`、`observe` 或 `skip` 及理由。
2. `participate` 时选择原创短帖、长帖/线程、引用转发或评论回复。
3. 引用或评论必须返回真实目标帖 URL；没有合适目标时改用原创或跳过。
4. 每个参与账号生成 3 条候选；不要求九个账号全部参与。
5. 系统统一状态和返回字段，不统一各账号的语气、长度和内容结构。

## 5. 候选与重新生成

1. 每个账号的 3 条合格候选全部进入该账号待发布区。
2. 同一账号对同一 Event 默认只能选择 1 条进入发布。
3. 选中后另外两条暂不可选；发布前可取消并改选。
4. 三条均不满意时可整批重新生成；无要求重生成或输入“更短”“换角度”“结合产品”等要求均可。
5. 重新生成默认仍返回 3 条，并重新执行适用预检。
6. 用户要求不能改变事实、绕过风险或突破账号 Skill。
7. 原始候选、用户要求、修改内容、预检结果和最终采用版本全部保留；默认展示最新版本。

## Constraints

- 每个触发响应的账号 Skill 正常输出必须为 3 条 DRAFT，而不是 1 条。
- 所有 Skill 只消费 Event Context Pack，不从页面 Event Card 或来源页面临时补事实。
- 产品账号不得拒绝已路由 Event，但品牌露出不得变成虚假的事件—产品关系。
- `quiet_presence` 仍产生产品账号草稿，但正文禁止商业露出。
- 人设 Skill 可以跳过；三条基础生产线不可因内容不相关而静默跳过。
- 所有内容仍受平台事实、风险、人工发布和审计合同约束。

## Non-goals

- 本 SPEC 不定义 X 自动发布、URL 回填、效果追踪或系统级风险门禁。
- 不要求九个人设账号全部参与同一 Event。
- 不用无限提高单账号频率解决容量问题；容量不足通过队列和新增同类型账号处理。
- 不统一不同账号的实际文风、长度和结构。

## Acceptance Criteria

- **AC-01 统一输入：**热搜、主题圈和未来事件形成的同一 Event 向所有 Skill 提供同一种 Event Context Pack。
- **AC-02 三线响应：**一个自动响应 Event 为三条基础生产线的每个可用绑定账号分别建立唯一任务。
- **AC-03 三候选：**每个触发响应的账号任务交付 3 条账号专属 DRAFT；重新生成后仍为 3 条。
- **AC-04 多账号扩容：**快讯生产线增加第二个账号后，两个账号具有独立任务和候选，且不重复同一账号任务。
- **AC-05 产品全量：**无真实市场关系时返回 `ambient_brand`，敏感事件返回 `quiet_presence`，两者均不返回跳过且不虚构关联。
- **AC-06 人设判断：**九个账号 Skill 分别返回参与、观察或跳过；参与账号形成 3 条候选。
- **AC-07 目标帖：**引用或评论候选缺少真实目标帖 URL 时不能作为该行动形式交付。
- **AC-08 版本：**候选修改和重新生成后，旧版本、用户要求和预检结果仍可追溯。

## Success signal

任一 Event 无论来自何种入口，都能以同一 Event Context Pack 驱动三条基础生产线；每个绑定账号建立独立任务并生成 3 条候选。产品账号始终形成真实边界内的草稿，人设账号独立判断参与，新增同类型账号可以扩大容量而不改变生产线合同。

## Open Questions

- 三条基础生产线首期分别绑定哪些具体 X 账号，由账号配置阶段确定。
