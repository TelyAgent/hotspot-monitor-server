> **Canonical contract.** 本文件定义热点运营平台的共同业务规则和跨模块合同。主题圈雷达、未来事件运营排期和热点内容生成的完整专项规则由 `companions:` 中对应 SPEC 唯一维护；本文件不复制其内部阈值和明细。

# 热点运营平台总规则 SPEC

## Why

平台需要把实时热点、主题圈讨论和未来事件统一转化为有证据边界的 Event，再为适配账号生成候选、完成风险预检、支持人工发布与结果追踪。统一规则的价值在于：来源可以不同，但事实、事件、内容和审计不能形成互相冲突的多套合同。

## 产品边界与页面术语

一级页面统一为：

1. `运营总览`：结果指标、人工待办、异常和任务进度。
2. `热点监测`：X 五地区榜单、重点主题、主题圈信号与具体热点入口。
3. `运营排期`：未来事件、证据、时间、窗口、热力和响应优先级。
4. `事件管理`：Event、事实、证据、归并拆分、来源上下文和响应状态。
5. `内容发布`：账号任务、候选、选择、修改、复制发布和 URL 回填。
6. `复盘优化`：发布效果、风险命中、异常原因和规则建议。
7. `系统设置`：来源、触发、账号 Skill、风险、权限和版本。

## 核心术语

- `Signal`：榜单快照、主题圈帖子、官方来源更新或人工输入中的原始信号；不是已确认事实。
- `Event Intake`：任何来源写入 Event 前的统一结构化输入。
- `Event`：平台围绕一个具体事实、动作、结果、状态或口径维护的唯一事件记录。
- `Evidence Record`：支持、质疑或补充某项事实主张的来源记录。
- `Event Card`：Event 的统一后台记录与页面展示，不是独立业务实体。
- `Event Context Pack`：Event 向内容和营销模块提供的唯一上下文合同。
- `Account Response Task`：一个 Event 对一个账号的一次内容响应单元。
- `Content Candidate`：绑定 Event、账号与 Skill 版本并通过适用预检的候选内容。
- `Publication Record`：人工发布后的 URL、账号、候选版本与追踪状态记录。

## Capabilities

- **CAP-1 多来源事件发现**
  - **intent:** 平台可以从 X 热搜、主题圈、未来事件和人工输入发现值得处理的具体事件。
  - **success:** 每次进入均记录来源、观察时间、触发依据和规则版本；来源失败或未启用不制造 Signal。
- **CAP-2 统一 Event 形成**
  - **intent:** 平台可以把不同来源的同一核心事实收敛成唯一 Event，同时区分新的事实发展。
  - **success:** 相同事实复用 Event ID 并追加来源上下文；新的动作、结果、更正或反转形成独立关联 Event。
- **CAP-3 事实、证据与表达边界**
  - **intent:** 平台可以在来源有限或冲突时继续处理，同时避免把不确定信息写成确定事实。
  - **success:** Event 保存已确认、未确认和冲突事实及 Evidence；所有下游均遵守当前 Confirmation Level 与 Expression Boundary。
- **CAP-4 多账号内容响应**
  - **intent:** 平台可以针对同一 Event 运行适配账号和内容 Skill，形成账号专属候选。
  - **success:** 每个参与账号建立唯一任务并生成规定候选或明确异常；候选不能跨账号复用，账号或 Skill 不可用不阻塞其他账号。
- **CAP-5 风险与预检**
  - **intent:** 平台只把符合事实、平台、法律、品牌和产品底线的候选交付正常待发布区。
  - **success:** 候选完成统一预检；失败处理、重生成、人工审核和最终版本均可追溯，高风险不得绕过门禁。
- **CAP-6 人工发布与回填**
  - **intent:** 内容运营可以在系统中选择或修改候选，在 X 人工发布并回填真实结果。
  - **success:** 同账号同 Event 最多选择一条发布；有效 URL 属于配置账号且不重复，未发布可记录失败或放弃原因。
- **CAP-7 效果追踪与复盘**
  - **intent:** 平台可以把发布记录转化为持续可观察的结果和规则改进依据。
  - **success:** 发布完成与数据追踪状态分离；接口异常不改写发布结果，历史指标、阈值与规则版本可追溯。
- **CAP-8 异常、权限与版本治理**
  - **intent:** 平台可以局部恢复失败并控制规则、来源、账号和人工覆盖权限。
  - **success:** 技术失败只重试失败步骤最多 3 次；成功数据保留，三次失败进入人工处理，所有配置与覆盖有审计。
- **CAP-9 运营排期衔接**
  - **intent:** 未来事件可以在人工请求或专项规则的自动门槛下进入平台统一 Event 与下游链路。
  - **success:** 运营排期始终先创建或复用 Event，再通过 Event Context Pack 进入内容或营销；具体来源、热力、评分和窗口遵循未来事件专项 SPEC。
- **CAP-10 主题圈衔接**
  - **intent:** 主题圈关注度可以作为独立于 X 热搜的充分触发路径进入统一 Event 链路。
  - **success:** 主题圈按专项 SPEC 判断同一事件和触发阈值；命中后复用平台 Event、证据、内容与发布合同。

## 1. X 热搜触发

首期每小时采集 Worldwide、United States、United Kingdom、Japan、Korea 五个榜单，每榜 Top 30。只有成功采集形成快照；失败采集不参与排名变化。

以下任一规则独立触发完整响应：

| ID | 条件 |
|---|---|
| TR-01 | 具体 Event 首次进入任一目标榜单第 1–5 位 |
| TR-02 | 同一 Event 在相邻两次成功小时快照间上升至少 10 位 |
| TR-03 | 具体 Event 语义命中已配置重点主题 |
| TR-04 | 同一具体 Event 同时出现在至少两个目标地区榜单 |

四条路径均不等待人工“是否参与”。`T0` 只记录系统首次成功发现合格触发的时间；当前不规定 T0 到自动校验完成的最长 SLA。

每个出现地区使用 X 默认热门排序，获取实际可取得的最多 3 条代表帖子；不足时按实际数量继续。帖子证明的是 X 上正在传播的说法，不当然证明现实事实为真。

## 2. 主题圈与未来事件入口

- 主题圈与 X 热搜是两条独立且充分的触发路径，完整账号清单、采集、B3h/B24h/Tmax 和触发阈值只在[主题圈雷达 SPEC](../spec-topic-circle-radar/SPEC.md)维护。
- 未来事件的来源、证据、窗口、Post Count、Action Score、75/90 分动作和时间变化只在[未来事件运营排期 SPEC](../spec-future-event-operations/SPEC.md)维护。
- 专项入口一旦决定形成响应，必须进入下述统一 Event 合同；不得建立主题圈 Event、热搜 Event 和排期 Event 三套数据结构。

## 3. Event Intake

所有来源先产生 Event Intake。最小字段包括：

| 字段组 | 内容 |
|---|---|
| 标识 | `schema_version`、`intake_id`、`entry_mode`、`observed_at` |
| 事件核心 | 标题、主体、事件类型、一句话事实摘要 |
| 事实与边界 | 确认状态、表达边界、已确认与未确认事实 |
| 证据 | `evidence_records[]` 与原始来源标识 |
| 时间 | 事实时间、时区与运营窗口；不适用时为空 |
| 来源上下文 | `trend_context`、`topic_circle_context`、`schedule_context` 可并存 |
| 响应 | 触发原因、评分及规则版本；不适用时为空 |
| 关联 | 候选 Event、去重键和更新时间 |

缺失字段保持空值，不得填充虚假值。同一 intake 可幂等重试。

## 4. Event、Card 与 Context Pack

Event 拥有不可变 `event_id`、首次进入方式和可并存的 `source_contexts[]`。主体、对象、动作、时间和当前事实含义一致时复用 Event；仅地区、榜单、表达、语言、排名、热度或来源不同不得新建。

新的动作、结果、状态、正式落地、口径更正或反转创建独立 Event，可建立前置、后续、落地、结果、更正或反转关系。旧 Event、旧内容和已发布记录不修改。

Event Card 共同展示标题、事实摘要、Evidence、核验与表达边界、状态、关联 Event、任务和审计；只按实际来源展示扩展区块：

- 热搜：榜单、地区、排名、变化、触发原因和代表帖子。
- 主题圈：圈层、讨论账号、触发指标和关联帖子。
- 排期：事实时间、精度、窗口、Action Score、Heat Query 和热力。

Event Context Pack 是内容与营销的唯一输入，至少包含 Event ID、状态、事实、未确认项、Evidence、表达边界、时间、关联 Event、触发与来源上下文。下游不得直接读取页面状态或绕过上下文包补造事实。

Event Card 与 Event Context Pack 使用同一 Event 数据，但用途不同：Event Card 是供运营人员查看、校正、合并、拆分和处理异常的页面；Event Context Pack 是不同事件源归并后向内容和营销模块提供的统一结构化数据合同。热搜、主题圈、未来事件和人工入口不得各自定义内容生成输入。

### 4.1 关联 Event 召回

1. 程序按主体、对象、语义关键词和时间召回少量历史 Event 候选。
2. 大模型只在候选集合内判断是否属于同一具体发展线，不无边界扫描数据库。
3. 最多向下游提供 3 条最相关关联 Event；不足 3 条按实际数量。
4. 关联类型包括前置、后续、正式落地、结果、更正和反转；当前 Event 始终是内容的主要事实。

### 4.2 更新与候选有效性

- 仅新增地区、榜单、排名、热度、跨区状态或重复来源时，只更新 Event Card 与 Context Pack，不自动重新生成内容。
- 新关联 Event 出现后，原 Event 的未发布候选标记`已有新进展`并暂停直接发布。
- 候选与最新事实冲突时标记`内容可能已失效`并禁止复制；运营人员必须修改、使用新 Event 或基于最新 Context Pack 重新生成。

## 5. 内容生成与账号任务

平台内容能力分为快讯型、长文/深度分析型和产品承接型三条基础生产线，以及独立账号运营 Skill，完整清单与输出边界只在[热点内容生成 Skill SPEC](../spec-hotspot-content-generation-skill/SPEC.md)维护。

共同规则：

- 每个 Account Response Task 绑定唯一 Event、账号和 Skill 版本。
- 生产线定义内容能力，账号定义发布身份；一条生产线可以绑定一个或多个同类型账号，每个账号分别建立任务。
- 每个被触发响应的账号 Skill 必须生成 3 条账号专属候选；生成失败记录明确异常，不以单条草稿代替三候选合同。
- 三条基础生产线对每个自动响应 Event 固定触发；九个人设账号各自返回参与、观察或跳过，参与账号再生成 3 条。
- 快讯只陈述一个核心事实；长文/深度分析区分已知、未知与后续观察；产品账号对每个路由 Event 均生成草稿。
- 产品承接有真实关系时使用`market_bridge`，无真实关系时使用`ambient_brand`，敏感伤害事件使用`quiet_presence`；不得虚构产品、市场、价格、概率或链接。
- 人设账号可选择原创短帖、长帖/线程、引用或评论；引用或评论必须返回真实目标帖 URL，没有合适目标时改用原创或跳过。
- 所有候选均为审核草稿，不代表自动发布。
- 同一账号存在多个普通热搜任务时，默认按榜单排名从高到低处理；重点主题、跨区、主题圈和排期任务进入同一队列并按可配置业务优先级排序。
- 快讯型账号初始建议容量为每日 10–15 条；长期超过容量时增加同类型账号分担，不通过绕过账号规则无限提高单账号频率。

### 5.1 候选与 AI 交互

1. 每个账号的 3 条合格候选全部进入该账号待发布区。
2. 同一账号对同一 Event 默认只能选择 1 条进入发布；选中后其他两条暂不可选，正式发布前可取消并改选。
3. 三条均不满意时可整批重新生成；既可直接重新生成，也可输入“更短”“换角度”“结合产品”等要求。
4. 重新生成默认仍返回 3 条，并重新执行适用预检。
5. AI 读取最新 Event Context Pack、账号 Skill、当前候选和用户要求；用户要求不得改变事实、绕过风险或突破账号规则。
6. 原始候选、用户要求、修改版本、预检结果和最终采用版本均保留，默认展示最新版本。

## 6. 风险与内容预检

统一风险覆盖平台规则、事实、法律、品牌、产品与金融表达。每条候选至少检查：

1. Event Context Pack 与 Evidence 一致性；
2. 未确认、冲突、预测和推断的表达边界；
3. 平台禁用表达与格式；
4. 品牌、法律、产品和金融风险；
5. 账号与 Skill 版本约束。

预检失败候选不得进入正常待发布区；可自动修正或重生成最多 3 次。高风险必须由授权人员人工处理，任何账号 Skill 都不能绕过系统统一底线。

风险结果统一为：

- `低风险`：正常进入待发布区。
- `中风险`：可生成并进入待发布，但显示简短风险提示和谨慎口径。
- `高风险`：只生成内部参考草稿，禁止复制发布，等待授权人员处理。
- `禁止生成`：无法安全改写的严重违规，只记录 Event 和原因，不生成草稿。

运营负责人或系统维护人员可对高风险选择：解除限制后重新预检、修改后重新预检、禁止发布并关闭。解除不代表原内容可直接发布；操作人、时间、原因和处理意见必须记录。

预检最多处理 3 次后：

- 3 条均合格：正常交付。
- 只有 1–2 条合格：标记内容异常并暂停正常发布；人工可接受现有合格内容、继续生成或放弃。
- 没有合格候选：不进入正常待发布区；人工只能继续生成或放弃。

原始生成、风险类型、触发片段、自动修改、每次预检、最终版本和人工处理结果回流复盘；敏感信息按规则脱敏。复盘只能提出优化建议，不能自动修改线上规则或 Skill。

## 7. 人工发布与 URL 回填

- 系统不自动向 X 发布，也不使用 Telegram 作为当前链路入口。
- 内容运营在同一账号任务中选择一条候选，可修改或重生成；修改后重新预检。
- 运营人员复制内容到 X 人工发布，再回填实际 URL 或失败/放弃原因。
- URL 必须格式有效、属于任务配置账号且未被其他发布记录使用。
- 有效 URL 回填即表示发布完成；追踪接口失败只改变追踪状态，不改变发布状态。
- 发布失败不占用“同账号同 Event 最多发布 1 条”的名额；运营可改选、修改或重新生成后再次尝试。
- 长期未发布任务不自动关闭，持续显示在运营总览；人工放弃时必须记录操作人和原因，并标记`已关闭—未发布`。

## 8. 效果追踪

- 发布后前 24 小时每 2 小时抓取一次；之后每 5 小时一次，默认至少追踪 7 天。
- 展示点赞、回复、转发，并在接口支持时记录引用和浏览量。
- 发布后 48 小时内浏览量达到 1000 时，标记表现良好并延长追踪至 14 天。
- 阈值、观察窗口和期限均可配置、版本化；数据缺失或接口失败必须如实显示。

### 8.1 完成状态与已完成事件库

- 账号任务在一条候选人工发布、有效 URL 已关联 Event/账号/候选，且追踪已建立或单独标记追踪异常后，记为`已完成`。
- Event 只有在全部参与账号进入`已完成`或`放弃发布`终态，且至少一个账号成功发布时，才进入已完成事件库。
- 全部账号都放弃时，Event 标记`已关闭—未发布`，不算响应完成。
- 已完成事件库列表展示 Event、发布账号数、内容数、发布时间、汇总互动、最近变化和更新时间；详情展示各账号原帖、数据曲线、追踪异常、放弃与处理记录及关联 Event。

## 9. 营销活动与 KOL 边界

命中以下任一机会时，系统主动提醒运营人员可以探索活动：重大可预见事件、竞品或行业活动、自有产品或品牌里程碑、具有明确参与机制的当前热点。运营人员也可以对任意 Event 随时主动探索活动；提醒本身不自动创建或执行活动。

每轮固定提供 3 个机制明显不同的候选，可整批重生成。每个候选至少包含名称、机制、匹配理由、目标、受众、渠道、时间、产品承接、就绪程度和准备缺口。系统可以推荐值得做但尚缺能力的方案，但必须明确产品、页面、预算、奖励、集成、资源或负责人缺口；重大可预见事件允许在承接尚未完善时提前生成方案。

选定后交付完整方案，包括概述、目标与用户行为、受众、机制和规则、内容概念、渠道与合作、产品承接、时间线、资源、风险、建议指标和下一步人工工作。方案可以修订、导出或交接外部团队，但平台不自动审批预算、创建投放、上线活动或执行外部动作。

KOL 只作为活动方案中的可选传播资源建议；平台不建设独立 KOL 工作流，不自动联系、议价或发送私信。

## 10. 异常、权限和版本

- 技术失败只从失败步骤立即重试，最多 3 次；不从头重跑，不覆盖成功数据。
- 单一来源或账号失败不阻塞其他对象；三次失败后进入人工处理并持续显示影响范围。
- 全链路监测覆盖采集、帖子获取、Event 识别与归并、摘要、关联、账号生成、预检、待发布、URL 回填和效果追踪；每个环节至少记录状态、开始与完成时间、失败原因、重试次数、影响范围和人工入口。
- 普通运营人员处理候选、回填、放弃和一般异常；运营负责人处理高风险、触发/窗口覆盖和升级异常；系统维护人员管理来源、账号 Skill、风险及系统配置。
- 触发、风险、账号 Skill、内容效果、来源、字段映射和窗口/评分规则均须版本化。
- 新版本默认影响新 Event 或新任务；在途对象沿用启动时版本，除非授权迁移并完整审计。

## Constraints

- Signal、热门帖子、主题圈讨论和热搜排名都不当然等于现实事实确认。
- 所有生成必须经过 Event 和 Event Context Pack；任何页面、来源或 Skill 不得建立旁路。
- 系统不自动向社媒发布，不把草稿、选择或复制显示为发布完成。
- 来源冲突可以继续形成受限候选，但不能被写成唯一确定事实。
- `internal_only`、`blocked` 和高风险门禁不能被评分、账号 Skill 或人工普通权限绕过。
- 历史 Event、Evidence、规则版本、内容和发布记录不得静默覆盖。

## Non-goals

- 不定义主题圈、未来事件或内容 Skill 的内部清单和阈值；这些由专项 SPEC 维护。
- 不实现私域触达、自动 KOL 外联或营销活动自动执行。
- 不自动发布 X，不处理删帖和编辑后的完整复杂生命周期。
- 当前不规定 T0 到自动校验完成 SLA，也不规定异常通知后的强制处理期限。

## Acceptance Criteria

- **AC-01 热搜采集：**一次成功采集保存五地区各 Top 30；失败采集不形成比较快照。
- **AC-02 四类触发：**前 5、相邻成功快照上升 10 位、重点主题和至少两地区均可独立触发。
- **AC-03 证据降级：**代表帖子不足 3 条时继续处理；来源冲突时限制表达但不伪造确认。
- **AC-04 Event 去重：**同一核心事实跨来源复用一个 Event；新结果建立独立关联 Event。
- **AC-05 统一输入：**热搜、主题圈、排期人工与排期自动入口均通过 Event Intake 和 Event Context Pack。
- **AC-06 多账号：**参与账号各形成唯一任务和 3 条候选或明确异常；单账号失败不阻塞其他账号。
- **AC-07 风险门禁：**失败候选不进入正常待发布，高风险未经授权不能继续。
- **AC-08 人工发布：**无有效 URL 或失败/放弃原因不能关闭任务；追踪失败不改写发布完成。
- **AC-09 专项一致性：**主题圈触发、未来事件 75/90 分行为和内容 Skill 输出分别通过对应 companion 的验收。
- **AC-10 局部恢复：**失败步骤最多重试 3 次，成功数据保留并可追溯恢复动作。
- **AC-11 Context Pack：**同一 Event 的所有来源上下文进入统一 Event Context Pack，内容 Skill 不直接读取页面 Event Card。
- **AC-12 关联与失效：**最多 3 条相关历史 Event 进入上下文；出现冲突新进展后旧候选无法直接复制。
- **AC-13 候选交互：**一个账号的 3 条候选只能选择 1 条；取消后可改选，重新生成仍返回 3 条并保留历史。
- **AC-14 完成事件：**全部参与账号终态且至少一条有效发布后 Event 才进入已完成事件库；全部放弃标记关闭未发布。
- **AC-15 活动机会：**四类机会任一命中时产生主动提醒，用户也可对任意 Event 主动探索，系统只交付方案。

## Success signal

任一有效来源进入后，平台能够形成或复用唯一 Event，以受证据约束的 Event Context Pack 驱动账号专属候选和统一预检；运营人员完成人工发布与 URL 回填，平台持续追踪结果。主题圈、未来事件和内容 Skill 可以独立演进，但不会改变共同 Event、事实、风险、发布和审计合同。
