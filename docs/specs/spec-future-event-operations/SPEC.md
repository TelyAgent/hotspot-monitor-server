# 未来事件运营排期 SPEC

## Why

平台既要响应已经发生的热点，也要提前管理时间可预见、值得持续监测和准备的事件。本模块把官方日历和人工关注项转化为有证据、有时间精度、有热力、有行动优先级的排期事件，并在人工请求或达到自动化门槛时，通过统一 Event 合同进入内容与营销链路。

## Capabilities

- **CAP-1 未来事件接入**
  - **intent:** 系统和授权运营人员可以从首版官方来源或人工导入建立可信的未来事件池。
  - **success:** 每条事件具有来源、事实时间或未知状态、确认等级和同步记录；未启用来源不产生模拟事件。
- **CAP-2 标准化、去重与版本**
  - **intent:** 系统可以把多来源的同一具体未来事件收敛为一个持续更新的排期对象。
  - **success:** 同一主体、事件类型、计划动作和对应日程只形成一个排期事件，历史证据、旧时间和规则版本均可追溯。
- **CAP-3 证据与表达边界**
  - **intent:** 运营和下游模块可以根据证据确定程度安全地理解与表达未来事件。
  - **success:** 每条事件同时具有 Confirmation Level、Schedule Precision 和 Expression Boundary；证据不足、改期或取消时阻止越界对外表达。
- **CAP-4 持续热力监测**
  - **intent:** 系统可以按事件倒计时持续记录 X 帖子量、来源健康与匹配的实时 Signal。
  - **success:** 小时级 Post Count 被幂等保存并聚合为 6 小时桶；采集频率、基线与升温状态按本文件计算，缺失数据不被补造。
- **CAP-5 行动评分**
  - **intent:** 运营人员可以通过可解释的 100 分 Action Score 判断当前准备和响应优先级。
  - **success:** 每条事件展示五维分数、总分、状态、版本和依据；75 分与 90 分门槛产生规定动作，评分不改变事实确认或表达边界。
- **CAP-6 运营窗口**
  - **intent:** 系统可以建议并维护监测、预热、事件进行和结果跟进窗口。
  - **success:** 窗口与事实时间分开记录；时间变化后未开始、进行中和已完成工作按规则处理并保留审计。
- **CAP-7 统一 Event 上下文**
  - **intent:** 未来事件可以通过 Event Intake、Event 和 Event Context Pack 安全进入平台统一下游链路。
  - **success:** 排期页不能绕过 Event 直接生成；人工与自动响应均复用统一 Event ID、卡片和上下文包。
- **CAP-8 热搜与排期关联**
  - **intent:** 系统可以把排期事件和实时热搜上下文合并到同一核心事实的 Event 中。
  - **success:** 热搜命中只补充讨论信号，不替代官方 Evidence 或提高确认等级；相同事实不重复建 Event，新事实发展建立关联 Event。
- **CAP-9 时间与状态变化**
  - **intent:** 运营人员可以安全处理时间确认、改期、取消、提前发生和长期未确认。
  - **success:** 每类变化正确更新状态、窗口、评分和下游门禁，变更前后的时间、证据与已发布内容完整保留。
- **CAP-10 异常与恢复**
  - **intent:** 系统和维护人员可以在来源或处理步骤失败时局部恢复。
  - **success:** 失败步骤最多重试 3 次；三次失败后显示影响范围和人工入口，其他来源继续运行且成功数据不被覆盖。

## 1. 模块目的与边界

运营排期管理尚未发生、但值得提前准备的事件。它回答四件事：

1. 哪些未来事件值得关注。
2. 事件是否真的会发生、何时发生，以及证据来自哪里。
3. 当前讨论热度是否在升温。
4. 在不夸大事实的前提下，下游可以如何使用事件信息。

运营排期不代替实时热点响应：已经发生、正在爆发的事件进入`事件管理`。到达事实发生时间时，排期事件只自动切换为进行中监测、更新上下文包；仅到达发生时间不会自动发布内容、创建营销活动或调用下游。Action Score 达到 90 分时，事件会自动升级为正式 Event 并进入自动响应。

首版只管理当前自然年剩余时间的事件。进入下一自然年后再年度刷新，不维护跨年度事件池。

## 2. 事件来源

首版只接入下列五类来源。自动来源必须以官方链接作为 Evidence Record；聚合站只能发现候选，不能作为确认事件的证据。

| 来源 | 官方入口 | 导入方式与频率 | 首版范围与默认状态 |
|---|---|---|---|
| OPM 美国联邦假日 | https://www.opm.gov/policy-data-oversight/pay-leave/federal-holidays/ | 首次一次性录入或 CSV；年度刷新同步一次 | 当年剩余假日；`Fixed`、`Date`、`factual` |
| BEA 发布时间表 | https://www.bea.gov/news/schedule | 每日同步一次 | 当年剩余发布；来源有明确日期/时间时为`Confirmed` |
| BLS 发布日历 | https://www.bls.gov/schedule/news_release/bls.ics | 每日同步一次，解析官方 iCalendar | Employment Situation、CPI、PPI、JOLTS、ECI；`Confirmed` |
| FOMC 会议日历 | https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm | 每日同步一次 | 当年剩余会议；`Confirmed`、`Date range`，使用货币政策会议模板 |
| 人工导入 | 系统表单或 CSV | 提交后即时校验 | 行业大会、品牌节点、人物行程等；来源链接必填，默认`Needs verification` |

P1 可接入重点体育官方赛程和监管连接器；P2 可接企业 IR 观察和 SEC 确认，均不属于首版范围。

自动 Connector 必须配置 URL/API/iCal/文件方式、认证、同步频率、字段映射、时区、超时、最多 3 次重试、健康状态、最近成功时间及人工补录入口。未接通时显示`未启用`或`等待配置`，不得伪造同步结果。

## 3. 程序与大模型职责

程序是来源事实和写入系统的唯一执行者，负责：

- 按频率获取官方来源，解析日历或表格。
- 只保留同步当天至当年 12 月 31 日的未来条目。
- 校验字段、去重、创建或更新事件。
- 保存原始来源、Evidence Record 和同步日志。
- 技术失败最多重试 3 次；失败不生成模拟事件。

大模型只处理程序已校验的结构化候选，可完成标题标准化、分类、事件模板映射、已确认/未确认事实拆分和 Event Context Pack 文案补充。它不得：

- 直接抓取后写库。
- 改写原始日期、时间或来源链接。
- 提高 Confirmation Level。
- 猜测 FOMC 利率决定、会议结论或任何来源未支持的事实。
- 把没有准确时间的事件补成`Exact time`。

## 4. 事件字段与证据

每个排期事件至少保存：

- 事件名称、主体、类型、事实时间、时区。
- Schedule Precision、Confirmation Level、Expression Boundary。
- 一个或多个 Evidence Record：来源链接、来源类型、最后核验时间、支持的事实主张。
- Event Window、Action Score 及五维分数。
- 关键词、Heat Query 与版本、热力监测起始时间、帖子量时间桶、热度与数据新鲜度。
- 关联实时 Event、最近更新时间和规则版本。

事实时间描述事件何时发生；Event Window 描述运营在哪段时间做什么，二者不得混用。历史 Evidence Record 和状态变更不得删除。

### 确认状态与下游表达边界

| Confirmation Level | 含义 | Expression Boundary |
|---|---|---|
| `Fixed` | 由规则或确定日期依据的周期事件 | `factual` |
| `Confirmed` | 已有权威来源确认 | `factual` |
| `Expected` | 有可靠信号或惯例，但未最终确认 | `qualified` |
| `Needs verification` | 证据不足、冲突或待人工核验 | `internal_only` |
| `Changed / Cancelled` | 改期、取消或关键事实失效 | `blocked` |

Schedule Precision 单独记录为`Exact time`、`Date`、`Date range`、`Season/cycle`或`Unknown`。

- `factual`：只能陈述证据支持的事实。
- `qualified`：必须保留“预计、可能、尚未确认”等表达；不得虚构精确时间；必须使用上下文包中的来源。
- `internal_only`：不得生成对外内容。
- `blocked`：暂停关联草稿、排期和下游请求，等待人工复核。

## 5. Event Context Pack 与下游

每个事件向内容或营销模块提供唯一的 Event Context Pack，内容包括：事件说明、当前状态、已确认与未确认事实、Evidence Record、事实时间、Event Window 和 Expression Boundary。

它像一个受事实约束的提示词上下文，但不规定下游必须产出几条内容、发到哪个渠道、采用什么形式，或是否要创建营销活动。运营排期不能直接调用内容生成：必须先创建或复用关联 Event，再由 Event 把上下文送进统一内容生成入口。

排期人工响应和排期自动响应都创建与热搜榜触发相同的 Event 基础卡片和同一种内容输入格式，以首次进入方式 `entry_mode` 区分：`scheduled_manual_response`、`scheduled_auto_response`或`trend_trigger`。后续排期或热搜来源作为可并存上下文追加到同一 Event。所有 Event 统一保存标题、事实摘要、Evidence Record、核验结论、确认/表达边界、响应状态、关联 Event、时间记录和内容任务记录。排期 Event 额外显示事实时间、窗口、Action Score 和热度；热搜 Event 额外显示地区、榜单、排名变化和代表帖子。两者命中同一事件时合并为一张 Event 卡片，下游收到的是同一个 Event Context Pack。

所有来源先进入统一 `Event Intake`，再创建或更新 Event；Event Card 是后台记录和展示，Event Context Pack 才是给内容生成的统一输出。

### Event Intake 最小合同

| 字段组 | 必填内容 |
|---|---|
| 标识 | `schema_version`、`intake_id`、`entry_mode`、`observed_at` |
| 事件核心 | 标题、主体、事件类型、一句话事实摘要 |
| 事实与边界 | Confirmation Level、Schedule Precision、Expression Boundary、已确认与未确认事实 |
| 证据 | `evidence_records[]`，含链接、类型、核验时间、支持主张和原始标识 |
| 时间 | 事实时间、时区、Event Window；缺失时为空，不得补造 |
| 来源上下文 | `schedule_context` 和/或 `trend_context`，两者可以并存 |
| 响应 | Action Score、五维分数、`score_version` 和触发原因 |
| 关联 | 候选关联 Event、去重键和更新时间 |

`entry_mode` 只使用 `trend_trigger`、`scheduled_manual_response`、`scheduled_auto_response`。排期上下文保存来源、时间、窗口、Heat Query、热力桶与评分；热搜上下文保存榜单、地区、排名、变化、快照与代表帖子。缺失字段保持空值，不得填写虚假占位数据。

Action Score 只是排序和判断建议，不是人工生成门禁。运营人员可在任何分数和任何阶段主动要求下游生成草案或方案；系统必须先创建或复用排期人工响应 Event，下游读取最新 Event Context Pack 并遵守当前 Expression Boundary。`internal_only`与`blocked`不得生成对外内容。

## 6. 去重、变更与实时事件关联

同一主体、同一事件类型、同一计划动作，且日期或官方日程相互对应时，合并为一个排期事件。标题、语言或来源不同不构成新事件；同主题下不同的数据发布、比赛或活动不能合并。

证据、确认或时间变化时，重新计算窗口和 Action Score，并保留旧证据和变更历史：

- 时间确认：更新事实时间、精度、证据、倒计时、评分和窗口。
- 改期或取消：标记`Changed / Cancelled`，暂停草稿、排期和下游请求，人工复核后恢复。
- 提前发生：立即进入事件进行中监测并更新 Event Context Pack，不自动调用下游。
- 长期未确认：保持观察或储备，不自动使用确定口径。

当实时来源出现匹配 Signal 时，系统用主体、类型、关键词和时间窗口召回排期事件。相同核心事实只补充来源；出现新动作、结果、正式落地、口径变化或反转时，创建独立实时 Event 并关联旧排期事件。

## 7. 运营窗口

系统为每个事件建议四类窗口：

| 窗口 | 用途 |
|---|---|
| 监测窗口 | 跟踪事实、来源、时间与热度 |
| 预热窗口 | 识别账号、准备情景内容、检查产品承接 |
| 事件进行窗口 | 事件发生或官方信息发布时，优先实时更新与响应 |
| 结果跟进窗口 | 围绕结果、影响和后续解释准备内容 |

默认预热窗口：

| 类型 | 默认预热 |
|---|---|
| BLS / BEA 数据发布 | T-7 天至 T-48 小时 |
| FOMC 会议 | T-7 天至 T-48 小时 |
| 美国节假日 | T-14 天至 T-48 小时 |
| 行业大会 | T-14 天至 T-48 小时 |
| 事实时间未知的 `Expected` 事件 | 不自动进入预热 |

事件临近窗口从事实时间前 48 小时开始；进行窗口以来源支持的开始/结束时间为准。运营人员仅对特殊事件手动覆盖默认窗口，所有修改必须记录修改人、原因、版本与影响范围。

## 8. 热力追踪

### 数据范围

首版只使用 X `Post Count`：帖子量和帖子量增长。不接入点赞、转发、浏览、作者影响力或跨平台数据。

每个事件维护可版本化的 Heat Query。Count 只表示匹配该查询词的 X 帖子量，不代表事件事实已经确认，也不代表全网讨论量。

系统保存小时级 Count，并聚合为 6 小时桶：

- 窗口新增量：某个统计窗口内新增的帖子数。
- 累计讨论量：从 `heat_monitoring_started_at` 起，全部成功窗口新增量之和。
- 累计曲线只展示过去真实数据；不能画成预期上涨曲线。

### 自动监测节奏

热力监测在事实时间前 30 天启动。日期范围事件以 Event Window 开始时间倒推；没有确定事实时间的`Expected`事件不自动启动。

| 时段 | 采集频率 |
|---|---:|
| T-30 天至 T-7 天 | 每 48 小时 |
| T-7 天至 T-48 小时 | 每 24 小时 |
| T-48 小时至事件结束后 T+48 小时，含进行中 | 每 6 小时 |
| T+48 小时至 T+7 天 | 每 24 小时 |
| T+7 天后 | 停止自动采集 |

每次采集取回自上次成功采集以来可取得的小时级 Count，再聚合为 6 小时桶。因此每两天或每天调度一次，不代表丢失中间的 6 小时数据。首次启动可回填 X 最近 7 天可取得的小时数据，不得伪造更早历史。频率切换不得造成重叠窗口重复累计。

热度升温只改变页面提示和 Action Score，不改变上述采集频率。

### 页面指标和明确约束

| 指标 | 计算方式 |
|---|---|
| 最近 6h 帖子量 | 最近 6 个小时桶新增量之和 |
| 前 6h 帖子量 | 紧邻此前 6 个小时桶新增量之和 |
| 增长 | 最近 6h 减前 6h，并显示变化百分比；前 6h 为 0 时显示`新出现` |
| 当前关注强度 | 最近 6h 帖子量 ÷ 过去 7 天典型 6h 帖子量的中位数 |
| 累计讨论量 | 自监测开始的全部成功新增时间桶之和 |

为避免小样本噪声，采用以下约束：

1. 只有过去 7 天有完整的 28 个有效 6 小时桶，且基线中位数不少于 10 条帖子，页面才显示`x 倍当前关注强度`；否则显示`热度历史不足`。
2. 最近 6 小时新增至少 20 条帖子，并且达到 7 天基线中位数的 2 倍，或相较前 6 小时增长至少 100%，标记为`明显升温`。
3. 基线中位数少于 10 条、但最近 6 小时达到 20 条时，标记`新出现`，而不显示没有意义的高倍数。
4. `10`、`20`、`2 倍`和`100%`均为后台可配置、可版本化参数。

热力趋势图横轴使用实际日期时间，实线只画累计讨论量。运营窗口只作为标记或背景。热力格展示过去 7 天、每天四个 6 小时块的新增帖子量；颜色只表示同一事件近期的相对强度。没有数据必须显示缺失，不可当成零或补造曲线。

## 9. Action Score

Action Score 满分 100 分，是当前运营优先级，不代表事件发生概率，也不会提升 Confirmation Level。事件影响力和热度动量是核心判断；时间紧迫性只是辅助判断。到达发生时间本身不构成自动响应。

| 维度 | 分值 |
|---|---:|
| 事件影响力 | 0-30 |
| 证据可靠度 | 0-20 |
| 热度动量 | 0-30 |
| 时间紧迫度 | 0-10 |
| 内容可执行性 | 0-10 |

其中“事件影响力”固定拆成三个子维度，各 0-10 分：

| 子维度 | 判断的问题 |
|---|---|
| 影响范围 | 会影响多少人、多少行业或多大地域？ |
| 目标相关性 | 与目标用户、业务主题或产品场景是否相关？ |
| 结果重要性 | 结果会不会带来政策、价格、规则、行为或行业判断上的可解释变化？ |

事件影响力不看当前讨论量和增长，不看内容是否好做，也不看来源是否充分；它们分别属于热度动量、内容可执行性和证据可靠度，不能重复计分。

| 总分 | 建议状态 | 系统含义 |
|---:|---|---|
| 0-39 | 观察 | 继续监测事实、时间与热度 |
| 40-59 | 储备 | 完善关键词、证据和事件上下文 |
| 60-74 | 计划 | 更新预热建议与上下文包 |
| 75-89 | 值得响应 | 创建值得备案的待响应提醒，由运营人员决定何时触发 |
| 90-100 | 自动响应 | 自动创建或更新关联 Event，并启动自动响应链路 |

热度动量为 0 时，其他维度最高只能得到 70 分，因此系统不会给出`值得响应`建议。运营人员可以在任何阶段主动触发草案或方案，但该动作必须先创建或复用 Event，再进入统一生成入口。规则变更只影响后续重新计算，历史分数和版本保留。

### 进入响应机制与自动响应

当分数首次达到或重新达到 `75` 分，且事件不是`Needs verification`或`Changed / Cancelled`，系统自动创建或更新一张`待响应`卡。卡片展示评分和变化、热度、证据状态、当前窗口与 Event Context Pack。

- `75-89`：进入待响应并提示值得备案，不自动生成；运营人员可以立即触发，也可以在之后任意时间主动触发。
- `90-100`：自动创建或更新关联正式 Event，类型为`排期自动响应`。
- 分数回落到 75 以下且尚未人工处理：标记`热度回落`，但保留卡片和历史。

`75-89`的待响应卡不等于自动响应：运营人员自行选择继续观察、生成 Brief、生成营销方案或忽略。达到`90`分则是唯一自动化门槛：系统将排期事件升级为正式 Event，带入其证据、时间、窗口、Heat Query 和 Event Context Pack，随后按既有 Event 流程聚合匹配帖子和可用来源、核验事实，并启动自动账号响应、内容生成和风险预检。

当运营人员在运营排期点击`生成内容`或`生成营销方案`时，系统后台先创建或复用`排期人工响应`Event，再直接跳转统一内容生成输入或营销方案输入，并预填该 Event 上下文。用户不需要先经过事件管理页面，但不能跳过 Event。人工响应 Event 不启动自动账号响应或发布；若已有同一核心事实的自动或人工响应 Event，则复用它而不重复创建。

升级时，系统还会用事件关键词、主体和时间窗口匹配最近成功的 X 热搜榜快照。命中时，把榜单、地区、排名、排名变化和匹配代表帖子并入同一个 Event，作为下游生成内容的附加上下文；没有命中热搜榜也继续自动响应。热搜榜只说明讨论信号，不能当作事件事实证据，也不能提高确认等级。之后的热搜榜命中只更新同一个 Event，不会重复创建。`Expected` 事件可以自动响应，但生成内容必须保留不确定性表达；`Needs verification`和`Changed / Cancelled`永远不能自动响应。

## 10. 页面与异常

运营排期以月历为主视图，展示本月事件、确认状态、来源、窗口、Action Score、热力趋势和热力格，并可查看 Event Context Pack 与 Expression Boundary，再按需进入下游内容或营销模块。

来源同步、字段解析、时间转换、去重、评分和上下文包更新纳入监控：技术失败最多自动重试 3 次；三次失败后通知运营负责人并进入异常看板；来源冲突为`Needs verification`，不视为接口故障。人工可补充来源、校正字段、重新同步、跳过来源或关闭事件，所有操作留痕。

## Constraints

- 首版只管理同步当日至当前自然年 12 月 31 日的事件；下一自然年通过年度刷新重新导入。
- 首版来源只包括 OPM、BEA、BLS 指定经济日历、FOMC 和带来源链接的人工导入。
- 程序是来源获取、解析、校验、去重和写入的唯一执行者；大模型不得直接抓取后写库或改变原始事实。
- 官方来源优先；聚合站只能发现候选，人工导入不得伪装成官方确认。
- 事实时间与 Event Window 必须分开；没有来源支持不得使用 `Exact time` 或准确倒计时。
- Action Score 是运营优先级，不是发生概率；不得提高 Confirmation Level 或 Expression Boundary。
- `internal_only` 与 `blocked` 不能进入对外生成；到达事实发生时间本身不能启动内容或营销。
- 排期、热搜和人工入口必须经过统一 Event Intake；内容与营销只读取 Event Context Pack。
- 历史证据、旧时间、旧评分、旧 Event、已发布内容和规则版本不得被新状态静默覆盖。
- 热力指标与阈值必须可配置、可版本化；Post Count 不得被描述为事实确认或全网声量。

## Non-goals

- 首版不接入体育官方赛程、监管 Connector、企业 IR 或 SEC 确认。
- 不建立跨年度常驻事件池，不做无边界全网爬虫。
- 不接入点赞、转发、浏览、作者影响力或跨平台热力数据。
- 不预测事件结果，不补造时间、参与方、会议结论或结果链接。
- 不由运营排期直接决定内容账号、候选数量、发布渠道或营销执行。
- 不替代实时热点、内容生成 Skill、风险预检和人工发布各自的专项规则。

## Acceptance Criteria

- **AC-01 来源与年度边界：**五类首版来源可创建事件；自动同步只导入同步日至当年 12 月 31 日，未启用来源不产生模拟数据。
- **AC-02 官方证据：**自动事件可追溯官方 Evidence；人工导入缺少来源链接时无法提交且默认 `Needs verification`。
- **AC-03 模型边界：**模型改变日期、来源或确认等级的输出被程序拒绝且不写库。
- **AC-04 时间精度：**只有日期的已确认事件使用 `Date`，不显示小时级倒计时。
- **AC-05 表达门禁：**`Expected` 保留限定表达；`Needs verification` 与 `Changed / Cancelled` 无法进入对外生成。
- **AC-06 去重与历史：**同一具体日程的多来源合并；不同发布不合并；改期后旧时间和证据仍可查看。
- **AC-07 热力调度：**系统按 T-30、T-7、T-48h、T+48h、T+7d 边界切换频率，低频抓取仍回补可取得的小时 Count 且不重复累计。
- **AC-08 热力指标：**最近/前 6h、增长、关注强度和累计讨论量按固定口径计算；不足 28 个桶或基线中位数低于 10 时显示历史不足。
- **AC-09 评分：**五维权重为 30/20/30/10/10；热度动量为 0 时总分最高 70；人工覆盖不改变表达边界。
- **AC-10 75 分门槛：**首次或重新达到 75–89 分时创建或更新待响应卡，不自动生成内容或方案。
- **AC-11 90 分门槛：**首次或重新达到 90 分且边界允许时创建或更新唯一 `scheduled_auto_response` Event，并进入既有自动响应链路；分数回落不撤销已启动流程。
- **AC-12 人工响应：**运营人员可在任意分数和任意阶段点击生成；系统先创建或复用 `scheduled_manual_response` Event，再进入指定生成入口，不自动启动其他账号响应。
- **AC-13 热搜关联：**匹配热搜时将榜单上下文并入同一 Event；未命中不阻断响应，热搜不替代官方证据。
- **AC-14 时间变化：**改期或取消暂停受影响草稿与请求；提前发生只更新进行中监测，不因时间到达自动生成。
- **AC-15 Event 合同：**所有入口经过 Event Intake，卡片只展示存在的来源扩展字段，下游只接收 Event Context Pack。
- **AC-16 局部恢复：**单一 Connector 失败只重试该步骤 3 次，其他来源继续运行且成功数据保留。

## Success signal

在验收环境中，五类首版来源能够建立有证据和时间边界的未来事件；系统按固定倒计时采集真实 Post Count、计算五维 Action Score，并在 75 分生成待响应提示、90 分生成唯一自动响应 Event。人工请求、热搜匹配、改期、取消和来源失败均通过统一 Event 合同处理，不产生重复 Event、虚假事实或不可追溯的下游内容。
