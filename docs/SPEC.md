# 热点运营系统完整业务 SPEC

> 本文件是自包含的业务合同。实现、原型、PRD、测试和后续 AI Agent 必须直接遵守本文；`business-rules.md` 保留更长的解释性版本，但本文不依赖它才能理解关键规则。

## 1. Why

系统需要同时处理突发热点和可预见事件：自动发现值得响应的 X 热点，将平台上的热门说法整理成有证据边界的 Event，调用多账号内容规则生成候选并完成风险预检；运营人员只负责选择、编辑、人工发布、URL 回填和异常处理。系统还需要通过运营排期提前监测重大未来事件、启动预热内容与活动方案，并在发布后持续追踪效果。

## 2. 产品边界和最终页面术语

一级业务页面统一为：

1. `运营总览`：先看结果数据，再看人工待办、链路异常、任务进度和当前热点。
2. `热点监测`：完整展示五地区排行榜、重点主题、跨区聚合和热点内容分析入口。
3. `运营排期`：管理未来事件的日历、证据、热度、窗口、预热内容和营销准备。
4. `事件管理`：管理已形成的 Event、事实依据、归并拆分、关联关系、响应状态和异常。
5. `内容发布`：按账号执行候选生成、选择、AI 修改、复制发布、URL 回填和失败处理。
6. `复盘优化`：查看内容效果、生成版本、风险命中和异常原因。
7. `系统设置`：管理接口、触发、主题、账号 Skill、产品资料、风险、追踪、排期来源、权限和版本。

## 3. 核心术语

- `Signal`：一次榜单快照、官方来源更新、人工导入或其他来源中的原始信号。Signal 不是已确认事实。
- `Event`：系统根据当前证据形成的一个具体事实、动作、结果、状态或口径。
- `排期事件`：尚未发生、预计发生或时间待确认，但需要提前监测和准备的事件。
- `T0`：一次成功采集首次发现满足自动触发条件的 Signal 的时间。
- `候选内容`：某账号针对某 Event 生成并经过适用预检的可选内容。
- `账号任务`：一个账号针对一个 Event 的一次内容响应执行单元。
- `关联 Event`：与当前 Event 属于同一具体发展线的前置、后续、落地、结果、更正或反转事件。

## 4. Capabilities

- **CAP-1 热点采集与自动触发**
  - **intent:** 持续采集五个 X 榜单，并用明确阈值触发自动响应。
  - **success:** 每个成功小时快照保存五榜 Top 30；前 5、相邻成功快照上升至少 10 位、重点主题命中、至少两地区同时出现四条路径均可独立触发并留痕。
- **CAP-2 Event 形成与事实约束**
  - **intent:** 将热搜表达转化为有一句话摘要、来源、核验状态和地区上下文的 Event。
  - **success:** 每地区按实际可取得数量使用最多 3 条 X 默认热门帖子；摘要不超过证据确定程度，冲突信息不被写成唯一事实。
- **CAP-3 Event 归并、拆分与关联**
  - **intent:** 避免同一核心事实重复响应，同时保留新的事实发展。
  - **success:** 同一核心事实跨地区、语言和快照合并；新的动作、结果、状态或口径创建独立 Event；最多提供 3 条最相关历史 Event 作为上下文。
- **CAP-4 多账号自动内容响应**
  - **intent:** 对每个触发 Event 自动运行基础账号和人设账号规则。
  - **success:** 快讯和解释账号固定响应；产品账号完成相关性判断；每个人设 Skill 独立决定参与及行动形式；每个参与账号生成 3 条候选。
- **CAP-5 风险与内容预检**
  - **intent:** 只向正常待发布区交付符合事实和系统风险底线的内容。
  - **success:** 候选完成五层预检；失败候选最多自动修正或重生成 3 次；风险、修改和最终采用版本全部可追溯。
- **CAP-6 人工发布与结果回填**
  - **intent:** 支持运营人员完成内容选择、AI 修改、人工发布和结果记录。
  - **success:** 同账号同 Event 最多发布 1 条；有效 URL 必须属于配置账号且不重复；失败可记录原因、重选、重生成或放弃。
- **CAP-7 效果追踪与完成事件库**
  - **intent:** 将已发布内容转化为持续可观察的结果记录。
  - **success:** 发布状态和追踪状态相互独立；按规定频率记录互动数据；满足完成条件的 Event 进入已完成事件库。
- **CAP-8 全链路异常与规则治理**
  - **intent:** 对采集、生成、预检、发布回填和追踪失败提供局部恢复。
  - **success:** 技术失败从失败步骤立即重试最多 3 次；三次失败通知运营负责人并持续显示；所有人工覆盖和规则版本留痕。
- **CAP-9 运营排期**
  - **intent:** 汇集系统内置、官方同步和人工导入的未来事件，形成可执行排期。
  - **success:** 排期事件具有证据状态、去重结果、监测关键词、100 分行动评分、四类窗口和热度追踪；进入预热后自动创建内容任务和活动入口。

## 5. X 榜单采集规则

### 5.1 目标榜单

首期固定采集：

1. Worldwide。
2. United States。
3. United Kingdom。
4. Japan。
5. Korea。

每个榜单采集 Top 30；一次完整成功采集最多形成 150 个榜单条目。

### 5.2 频率与快照

1. 榜单 API 每小时调用一次。
2. 只有成功采集才能形成快照并参与排名比较。
3. 快照至少保存榜单、地区、原始热搜词、当前排名和采集时间。
4. 排名变化只比较相邻两次成功小时快照。
5. 采集失败不形成新快照，不制造排名变化，也不触发“上升 10 位”。
6. 重点主题和跨区异动不额外提高采集频率。
7. 系统通过连续成功快照形成自己的排名趋势；X 不提供的历史曲线不得被虚构。

## 6. 自动触发与 Event 形成规则

### 6.1 四条独立触发路径

满足任一条即自动形成或归并 Event，并进入完整自动响应：

| 编号 | 触发条件 | 精确定义 |
|---|---|---|
| TR-01 | 前 5 触发 | 某个具体 Event 首次进入任一目标榜单第 1–5 位 |
| TR-02 | 上升 10 位触发 | 同一具体 Event 在相邻两次成功小时快照间排名上升至少 10 位；以前一快照排名减当前快照排名计算 |
| TR-03 | 重点主题触发 | 具体 Event 在语义上属于已配置重点主题；不要求主题名称本身出现在热搜词中，也不等待前 5 或上升 10 位 |
| TR-04 | 跨区异动触发 | 同一具体 Event 同时出现在至少 2 个目标地区榜单；不要求满足其他排名条件 |

附加约束：

1. TR-02 必须存在两次可比较的成功快照；前一快照没有可确认排名时，不能仅凭“新出现”认定上升 10 位，但仍可由其他三条规则触发。
2. 重点主题当前按宽泛主题词、语义关键词、正例和反例配置，例如 AI 主题可命中“GPT 新模型发布”。
3. 明显主题匹配由系统自动确认；无法确定的归属进入校正或异常处理，不得静默归类。
4. “目标群体中热度很高”尚未接入，本期不作为主题触发条件。
5. 跨区异动不是只标红或提高排序，而是直接启动完整响应；地区扩散可作为内容上下文，但不能脱离实际榜单证据夸大传播范围。
6. 四条触发均不等待人工“是否参与”判断。

### 6.2 自动响应路径

触发后的默认路径为：

`触发 → Event 形成/归并 → 事实摘要与核验 → 历史 Event 关联 → 基础账号和人设 Skill 响应 → 内容预检 → 内容发布待处理区`

人工从候选选择、编辑和发布开始介入。系统不设置触发后的人工审核前置门。

### 6.3 时间口径

1. `T0` 只记录系统首次成功发现合格触发的时间。
2. 当前不规定 `T0 → 自动校验完成` 的最长 SLA。
3. 事件完成检验和校准后立即进入生成，不设置人为等待的“5 分钟投递”业务步骤。

## 7. 热搜帖子与事实摘要

### 7.1 帖子获取

1. 对每个触发条目使用 X 返回的默认热门排序。
2. 每个地区最多取实际可取得的前 3 条帖子。
3. 只能取得 1–2 条时按实际数量处理，不补齐、不阻塞、不改用自定义排序。
4. 同一 Event 出现在多个地区时，每个地区分别最多取 3 条；全部帖子去重后合并并保留地区归属。

### 7.2 事实边界

1. 热门帖子证明的是“这些说法正在 X 上传播”，不当然证明现实事件为真。
2. 一句话摘要必须与证据确定程度一致。
3. 未确认信息使用“多个热门帖子称”“X 上正在讨论”等限定表达。
4. 不得因为三条帖子说法一致就自动宣称官方确认。

### 7.3 核验结论

- `信息一致`：当前依据在核心事实层面一致。
- `信息有限`：依据数量不足、关键字段缺失或只有单一来源。
- `存在冲突`：不同依据对同一核心事实给出不同说法。

存在冲突不停止自动流程，但内容只能描述目前有哪些说法，不得将其中一种写成确定事实。

## 8. Event 数据与生命周期

### 8.1 Event Card 最小字段

1. Event 标题。
2. 一句话事实摘要。
3. 当前排名及变化。
4. 出现地区。
5. 首次发现时间。
6. 命中原因：TR-01、TR-02、TR-03、TR-04 或组合。
7. 事实依据按钮及原帖链接。
8. 核验结论。
9. 当前响应状态。
10. 关联 Event。
11. 账号任务与完成情况。

事实依据在页面可显示为“依据 1/2/3”等入口，点击打开真实 URL；多地区 Event 可超过 3 条总依据。

### 8.2 同一 Event

核心事实未变化，仅出现以下差异时归并：

- 地区不同。
- 榜单不同。
- 发现时间或快照不同。
- 热搜词、语言或表达不同。
- 依据帖子不同但描述同一核心事实。

归并后更新地区、排名、跨区状态、热度和依据，不重复生成同一核心事实的内容。

### 8.3 新 Event

出现新的动作、结果、状态或口径时创建独立 Event，例如“宣布即将发布”和“正式发布”是两个 Event。旧 Event 和旧内容不修改。

新旧 Event 可建立：

- 前置事件。
- 后续进展。
- 正式落地。
- 结果公布。
- 口径更正。
- 事件反转。

### 8.4 关联召回

1. 程序按主体、对象、语义关键词和时间召回少量历史候选。
2. 大模型只在候选集合中判断是否属于同一具体发展线。
3. 最多选择 3 条最相关历史 Event；不足 3 条按实际数量。
4. 关联 Event 仅作当前内容上下文，当前 Event 始终是主要事实。

### 8.5 非事实变化

只新增地区、排名变化、热度变化、跨区状态或更多重复说法时，只更新 Event Card，不自动重生成内容。人工可要求 AI 基于最新上下文重新生成。

## 9. 账号响应体系

### 9.1 基础响应层

基础层包含快讯型、事件解释翻译型和产品承接型账号。

#### 快讯型

1. 覆盖所有触发 Event。
2. 每个 Event 生成 3 条原创候选。
3. 单条只讲一个核心事实，通常 1–2 句。
4. 不做分析、不表达个人观点、不关联产品。
5. 可使用 `JUST IN/快讯`、`LIVE`、`UPDATE`；`BREAKING` 仅用于重大且事实明确的事件，信息有限或冲突时禁止使用。
6. 初始建议容量为每日 10–15 条，可在系统设置中调整。

#### 事件解释翻译型

1. 覆盖所有触发 Event并生成 3 条候选。
2. 补充必要背景、解释专业概念和关注原因。
3. 明确区分已知、未知和后续观察点。
4. 可读取最多 3 条关联 Event。
5. 单条、长帖或线程由该账号 Skill 决定。
6. 不负责产品承接。

#### 产品承接型

每个 Event 都要完成承接判断：

- `直接承接`：存在与 Event 直接相关且当前可用的预测市场、功能、页面或活动及真实链接；生成 3 条候选。
- `自然相关`：产品现有一般能力可自然服务该需求，但没有一一对应入口；生成 3 条候选，不得假装已有专门页面。
- `无关`：必须生硬插入品牌或产品不能帮助用户理解、判断或参与；跳过并返回原因。
- `产品资料不足`：无法核验能力、链接或状态；不生成。

产品特性、目标用户、已上线能力、限制、真实资源和链接必须预先写入系统；模型不得编造功能、市场、价格、概率、状态或链接。

### 9.2 人设账号层

1. 九个人设账号的 Skill 是运营规则，不是纯文风模板。
2. 每个核验 Event 分别交给各账号 Skill。
3. 大模型按 Skill 独立决定参与、观察或跳过。
4. 参与时自行选择符合定位的响应角度和行动形式。
5. 支持原创短帖、长帖/线程、引用转发和评论回复。
6. 引用或评论必须返回真实目标原帖；没有合适目标时改用原创或跳过。
7. 每个参与账号生成 3 条候选；不要求九个账号全部参与。
8. 系统统一返回字段，不统一实际语气、长度和结构。

### 9.3 多热点队列和账号容量

1. 同一账号同时存在多个热点任务时，默认按榜单排名从高到低处理。
2. 重点主题、跨区异动等直接触发 Event 进入同一队列，并按可配置业务优先级排序。
3. 快讯型账号长期超过每日 10–15 条容量时，应增加同类型账号分担，不通过无限提高单账号频率解决。

## 10. 候选内容和 AI 交互

1. 每个参与账号的 3 条候选全部进入该账号待发布区。
2. 人工从中选择 1 条进入发布；同账号同 Event 默认只能发布 1 条。
3. 选中后其他两条暂不可选；正式发布前可取消并改选。
4. 三条均不满意时可整批重新生成。
5. AI 窗口支持无要求重生成，或输入“更短”“换角度”“不要提产品”等要求。
6. AI 同时读取当前 Event、最多 3 条关联 Event、账号 Skill、当前候选和用户要求。
7. 重新生成默认仍返回 3 条。
8. 用户要求不得改变事实、绕过风险或突破账号 Skill。
9. 旧版本保留，默认展示最新版本。
10. 关联新 Event 出现时，未发布旧候选标记`已有新进展`并暂停直接发布；与最新事实冲突时标记`内容可能已失效`并禁止直接复制。

## 11. 系统级风险与预检

### 11.1 五类统一风险

1. `平台规则风险`：暴力、仇恨、骚扰、隐私、冒充、垃圾营销、诈骗、恶意链接、非法交易、版权或平台限制。
2. `事实风险`：传闻确定化、人物数字错误、信息过期、冲突说法单一化或超出 Event 边界。
3. `法律风险`：未经证实的犯罪、欺诈、内幕交易等指控，以及诽谤、版权和监管限制。
4. `品牌风险`：消费灾难伤亡、生硬蹭热点、攻击群体或严重偏离品牌定位。
5. `产品与金融风险`：编造能力、市场、价格、概率或收益，暗示保证回报，忽略地区资格和可用性限制。

所有账号、Skill、内容及活动方案共用统一底线；局部规则只能更严格，不能降低底线。

### 11.2 风险等级

- `低风险`：正常生成并进入待发布。
- `中风险`：可生成，展示简短提示并使用谨慎口径。
- `高风险`：仅生成内部参考草稿，禁止复制发布，等待人工处理。
- `禁止生成`：无法安全改写的严重违规，只记录 Event 和原因，不生成草稿。

运营负责人和系统维护人员可选择：解除限制后重新预检、修改后重新预检、禁止发布并关闭。任何解除都不代表原内容可直接发布；操作人、时间、原因和处理意见必须记录。

### 11.3 五层内容预检

1. 平台合规。
2. 事实一致性。
3. 法律与品牌。
4. 产品信息。
5. 发布行为、账号、URL 和重复回填。

固定规则处理明确禁项，大模型理解语义，Event/产品数据核验事实和能力，程序检查账号、URL、目标原帖及重复行为。

### 11.4 预检失败

1. 失败候选不进入正常待发布区。
2. 系统按失败原因立即修改或重新生成，最多 3 次。
3. 仅通过预检的候选正常展示。
4. 3 次后仅有 1–2 条合格候选时标记异常并暂停发布；人工可接受现有内容、继续生成或放弃。
5. 没有合格候选时只能继续生成或放弃。
6. 原始版本、风险命中、触发片段、自动修改、最终版本和人工采用结果全部回流复盘；敏感内容脱敏。
7. 复盘只产生优化建议，不能自动修改线上规则或 Skill。
8. 正常内容发布页面只展示最终合格候选、简要风险状态和处理入口，不展示完整模型推理；详细版本链进入复盘优化和审计记录。

## 12. 人工发布与 URL 回填

1. 用户选择候选后获得复制入口，自行前往 X 发布。
2. 系统不自动发帖，也不替用户完成平台发布。
3. 发布成功必须回填 X URL。
4. 发布失败选择失败状态并记录原因。
5. URL 必须属于系统已配置且与当前内容对应的账号。
6. 格式错误、账号不匹配或重复 URL 不能提交，并立即提示。
7. 发布失败不占用“同账号同 Event 只能发布一条”的名额；可重新选择、编辑或重生成后再次尝试。
8. 长期未发布持续显示在运营总览；人工可继续处理或放弃。
9. 放弃必须记录操作人和原因，并标记`已关闭—未发布`；当前不设置自动关闭期限。

## 13. 完成状态与效果追踪

### 13.1 账号响应完成

满足以下条件即完成：

1. 一条候选已人工发布。
2. 有效 URL 已关联 Event、账号和候选。
3. 已建立数据追踪，或已发布但追踪单独标记异常。

### 13.2 Event 完成

1. 所有参与账号均进入`已完成`或`放弃发布`终态。
2. 至少一个账号已发布并回填有效 URL。
3. 全部账号都放弃时，Event 为`已关闭—未发布`，不算响应完成。

### 13.3 数据抓取

1. 发布后 0–24 小时每 2 小时抓取一次。
2. 24 小时后每 5 小时抓取一次。
3. 默认至少追踪 7 天。
4. 必须展示点赞、回复、转发；接口支持时记录引用和浏览量。
5. 发布后 48 小时内浏览量达到 1000，判定表现良好并把追踪期延长至 14 天。
6. 1000 浏览量、48 小时窗口和 14 天期限均可配置、可版本化。
7. 数据接口不可用不推翻发布完成，只标记`追踪异常`；立即重试 3 次，仍失败则通知运营负责人。

### 13.4 已完成事件库

列表展示 Event、发布账号数、内容数、发布时间、汇总互动、最近变化和更新时间。详情展示每个账号原帖、数据曲线、放弃结果、处理记录和关联 Event。

## 14. 营销活动与 KOL

### 14.1 活动机会

命中任一信号即可主动建议活动：

- 重大可预见事件。
- 竞品或行业活动。
- 自有产品或品牌里程碑。
- 具有明确参与机制的当前热点。

每个 Event 也允许用户随时主动探索活动。

### 14.2 活动候选与交付

1. 固定生成 3 个机制明显不同的候选，不满意可整批重生成。
2. 每个候选包含名称、机制、匹配理由、目标、受众、渠道、时间、就绪程度和准备缺口。
3. 可推荐“值得做但还缺能力”的形式，但必须标明产品、页面、预算、奖励、集成、资源或负责人缺口。
4. 重大未来事件允许在产品承接未完善时提前出方案。
5. 选定后交付完整方案：概述、目标与用户行为、受众、机制和规则、内容概念、渠道与合作、产品承接、时间线、资源、风险、建议指标和下一步人工工作。
6. 系统到方案交付为止，不创建项目、不审批预算、不实现功能、不上线活动。

### 14.3 KOL 边界

1. 首期不建设独立 KOL 业务界面。
2. KOL 只作为活动方案的推广建议。
3. KOL 数据由系统设置人工导入和维护，可包含覆盖、性价比等指标。
4. 系统不自动私信、不管理报价、不推进关系、不执行合作。

## 15. 运营排期

### 15.1 事件源

1. `系统内置`：全球节日、美国宏观日历、重点体育赛程。
2. `官方来源自动同步`：政府、赛事组织方、企业官方公告和官方日历。
3. `人工导入`：补漏和运营指定关注。

首期实际录入以人工批量导入为主。未接通的自动连接器必须显示`未启用`或`等待配置`，不得展示模拟同步结果。

### 15.2 来源配置

每个来源配置名称、类型、URL/API/iCal/文件接入方式、认证、同步频率、字段映射、时区、超时、3 次重试、健康状态、最近成功时间和人工补录入口。官方来源优先于媒体和人工描述；人工导入不能伪装成官方确认。

### 15.3 自动处理与字段

排期事件进入系统后自动完成：标准化、去重、摘要、证据状态、关键词、四类窗口建议、100 分评分、热度与来源追踪、内容和活动方向识别。

人工导入时可直接修改系统建议窗口；其他自动结果通过后续校正入口修改并留痕。

最小字段包括事件名称、主体、类型、日期/时间范围、时区、确认状态、来源、关键词、五维评分、建议状态、四类窗口、热度和新鲜度、关联 Event、任务、活动方案、更新时间和规则版本。

### 15.4 证据状态

1. `官方已确认`：事件和准确时间均有官方依据，可使用准确倒计时。
2. `事件确认·时间待定`：事件已确认但时间未确认，不得准确倒计时。
3. `可靠预期·尚未官宣`：有可靠支持但未官宣，只能表述为预期或窗口。
4. `信息冲突·仅观察`：来源冲突或关键字段不足，不得写成确定会发生。

历史来源与状态不得删除；变化会重算评分和窗口。

### 15.5 排期去重

主体、事件类型、计划动作和时间窗口指向同一发布、数据公布、比赛、节日或官方活动时合并。标题、语言和来源不同不构成新事件；同主题下不同发布、比赛或数据公布不得合并。官方新口径成为当前口径但保留历史。

### 15.6 持续监测与热度

事件进入排期即监测官方时间、地点、参与方、来源健康、关键词、X 榜单、讨论热度和匹配实时 Signal；不设置单独的可操作“准备窗口”。没有连续数据时显示`热度历史不足`，不得虚构曲线。

### 15.7 100 分行动评分

| 维度 | 分值 |
|---|---:|
| 事件影响力 | 0–25 |
| 证据可靠度 | 0–25 |
| 热度动量 | 0–25 |
| 时间紧迫度 | 0–15 |
| 内容可执行性 | 0–10 |

| 总分 | 状态 | 系统动作 |
|---:|---|---|
| 0–39 | 观察 | 监测事实、时间和热度，不创建发布任务 |
| 40–59 | 储备 | 完善关键词、来源和模板 |
| 60–74 | 计划 | 形成预热建议、情景结构和建议发布时间 |
| 75–89 | 激活 | 创建内容任务并准备活动候选 |
| 90–100 | 立即响应 | 立即创建快讯、解释和适用产品承接任务 |

评分是系统建议，不是不可覆盖的审批门禁；运营可提前启动或继续观察并留痕。`信息冲突·仅观察`不能因其他高分被写成确定事实。

### 15.8 四类窗口

1. `监测窗口`：进入排期后立即开始。
2. `预热窗口`：匹配账号、准备情景内容、检查产品承接并允许发布前期内容。
3. `事件进行窗口`：事件发生或官方信息发布，实时更新优先。
4. `结果跟进窗口`：结果或正式落地后生成解释和影响内容。

系统建议窗口，运营可修改。未开始任务按新窗口排期；进行中任务标记`窗口已变化`并重新检查；已发布内容不修改；修改人、原因、版本和影响范围留痕。

### 15.9 预热和实时 Event

进入预热窗口后自动匹配基础账号和人设账号、生成不同情景预案、检查产品承接、创建账号任务进入`内容发布`，并对重大事件提供活动候选入口。

实时 Signal 命中排期事件时：

1. 核心事实相同且只是新增来源，补充依据，不重复任务。
2. 新动作、结果、正式落地、口径变化或反转创建独立 Event。
3. 新 Event 进入`事件管理`，排期事件和最多 3 条历史 Event 作为上下文。
4. 旧排期、旧 Event 和已发布内容不覆盖。
5. 相同账号和相同核心事实的预热任务必须复用或更新，避免重复发布。

### 15.10 时间变化

- 时间确认：更新准确时间、证据、倒计时、评分和窗口。
- 改期：保留旧时间，重算窗口；未发布内容重新预检。
- 取消：停止未开始任务，进行中任务进入人工确认，可形成“已取消”新 Event。
- 提前发生：立即进入事件进行或立即响应。
- 长期未确认：保持观察/储备，不使用确定口径。

## 16. 全链路异常与恢复

监测步骤包括榜单抓取、热门帖子获取、Event 识别、摘要、关联、账号生成、预检、待发布、URL 回填、数据抓取，以及排期来源同步、解析、去重、评分和任务创建。

规则：

1. 技术失败只从失败环节立即重试，最多 3 次，不从头重跑。
2. 保留已成功数据；单个账号或来源失败不阻塞其他对象。
3. 三次失败后标记`需要人工处理`并通知运营负责人。
4. 异常持续显示在运营总览，直至恢复或人工关闭。
5. 人工可重新执行、补充信息、跳过或终止；所有动作留痕。
6. 当前不规定再次催办时间和强制处理期限。
7. 帖子不足 3 条是正常降级，不算技术失败。
8. 来源冲突属于证据状态；内容预检失败属于内容异常，分别走对应规则。
9. 每个监测环节至少记录当前状态、开始与完成时间、失败原因、重试次数、影响范围和人工处理入口。

## 17. 权限、配置与版本治理

### 17.1 权限

- `普通运营人员`：选择、编辑、重生成、复制、URL 回填、失败记录、放弃和一般异常处理。
- `运营负责人`：解除高风险、修改重点主题和监测、调整排期窗口、校正排期事件、提前启动任务、处理升级异常。
- `系统维护人员`：管理账号 Skill、风险、接口、排期来源、评分、系统配置，也可处理高风险。

### 17.2 必须版本化的对象

- 重点主题与触发规则。
- 风险和预检规则。
- 账号 Skill。
- 产品资料与承接配置。
- 内容效果阈值和追踪期限。
- 排期来源与字段映射。
- 排期证据、去重、评分和窗口规则。

每次修改记录修改前后、修改人、时间、原因和生效范围。新版本默认只影响新进入 Event 或新发布内容；在途对象沿用启动时版本。复盘建议必须人工确认才能成为线上新版本。

## 18. Constraints

1. 系统不自动向 X 发布。
2. 四条热点触发不等待人工参与决定。
3. 热门帖子不等于现实事实确认。
4. 冲突信息不阻断生成，但限制确定性表达。
5. 账号 Skill 不能绕过系统统一风险底线。
6. 产品能力、市场、价格、概率、状态和链接必须来自真实配置。
7. 未接通来源不得展示模拟同步结果。
8. 只有官方确认时间可使用准确倒计时。
9. 旧 Event、旧内容和历史规则版本不得被新状态静默覆盖。
10. 营销活动和 KOL 只交付建议或方案，不自动执行。

## 19. Non-goals

1. 当前不规定 `T0 → 自动校验完成` SLA。
2. 当前不规定异常通知后的再次提醒时间和强制处理期限。
3. 当前不建设独立 KOL 界面或自动触达。
4. 当前不定义私域触达完整规则。
5. 当前不自动审批活动预算、资源或上线。
6. 当前不处理 X 删帖和编辑后的复杂生命周期。
7. 当前不把目标群体热度作为重点主题触发源。

## 20. Acceptance Criteria

- **AC-01 五榜采集：**一次成功采集产生 Worldwide、美国、英国、日本、韩国各 Top 30 快照。
- **AC-02 前 5：**测试 Event 首次进入任一榜第 5 位时自动形成 Event 并进入响应；第 6 位且无其他条件时不由该规则触发。
- **AC-03 上升 10 位：**同一 Event 在相邻成功快照从第 18 位升至第 8 位时触发；升 9 位不触发；中间采集失败不生成比较快照。
- **AC-04 重点主题：**“GPT 新模型发布”语义命中 AI 主题，即使词面没有“AI”且排名低于前 5，也触发。
- **AC-05 跨区异动：**同一 Event 同时出现在任意两个目标地区榜单时触发，并聚合两地区去重后的帖子依据。
- **AC-06 帖子降级：**某地区只能取得 2 条默认热门帖子时，以 2 条形成摘要并继续处理。
- **AC-07 证据冲突：**两个来源说法冲突时 Event 标记`存在冲突`，内容只描述不同说法，流程继续。
- **AC-08 Event 归并：**同一核心事实在不同地区、语言和快照中只形成一个 Event；新结果形成独立关联 Event。
- **AC-09 基础账号：**每个触发 Event 的快讯和解释账号各形成 3 条预检候选；产品账号返回 3 条或明确跳过原因。
- **AC-10 人设账号：**每个 Skill 独立返回参与/观察/跳过和行动形式；参与账号形成 3 条候选。
- **AC-11 内容预检：**失败候选最多自动处理 3 次；不足 3 条时进入异常，不将失败内容放入正常待发布区。
- **AC-12 单账号单 Event：**三条候选中只能选一条进入发布；发布前可以取消和改选。
- **AC-13 URL 校验：**非配置账号 URL、格式错误或重复 URL 无法提交。
- **AC-14 发布与追踪分离：**有效 URL 回填后即记发布完成；追踪接口失败只标记追踪异常。
- **AC-15 数据频率：**发布后前 24 小时按 2 小时抓取，之后按 5 小时抓取，默认至少 7 天。
- **AC-16 良好内容：**48 小时内浏览量达到 1000 时延长至 14 天，并记录阈值版本。
- **AC-17 局部重试：**技术步骤失败只重试该步骤 3 次；成功数据保留；三次后通知运营负责人。
- **AC-18 排期证据：**未官宣事件不能使用准确倒计时；官方时间确认后自动重算状态、评分和窗口。
- **AC-19 排期预热：**进入预热窗口自动创建适配账号任务并进入内容发布；进入排期本身只启动持续监测。
- **AC-20 实时关联：**排期事件出现新的实际结果时形成独立 Event 进入事件管理，且不覆盖旧排期或重复同账号任务。
- **AC-21 营销活动：**每次活动探索生成 3 个机制不同候选，允许整批重生成；选定后只交付方案。
- **AC-22 规则版本：**规则修改后，新 Event 使用新版本，在途 Event 保留旧版本和完整审计。

## 21. Success Signal

系统可以稳定证明以下闭环：五地区任一条精确触发规则命中后，自动形成或归并 Event，基于实际可取得的热门帖子形成受证据约束的摘要，运行基础账号和适配人设 Skill，完成风险预检并把合格候选交付内容发布；运营人员可人工发布并回填有效 URL；系统持续追踪效果、形成已完成事件库和异常审计。未来事件可从三类来源进入运营排期，经证据、去重、评分和窗口进入预热，并在新实时事实出现时创建关联 Event。

3. 运营排期各类官方来源最终采用哪些 API、同步频率与授权方案？
